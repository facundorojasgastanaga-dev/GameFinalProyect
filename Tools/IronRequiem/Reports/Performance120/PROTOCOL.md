# Performance120Lab — protocolo v1

Objetivo: RTX 4050 Laptop, 1920x1080, D3D11, calidad Default sin cambios visuales, render scale original. VSync 0 y sin limite durante medicion; 120 FPS = 8,333333ms. No se considera el promedio como criterio de cierre. Registrar el porcentaje sobre presupuesto, P95/P99 y picos; CPU y GPU se evalúan por separado.

Escena: copia separada de CombatPerformanceLab, mismo NavMesh, materiales, iluminación, cámara FPS, Health/IA, T07_Common_Destructible, armas/carga/humo/explosión originales. No se modifican MainScene ni los prefabs. Se propone un presupuesto inicial de 16 T07 por oleada (12 con capacidad de disparar tras desprender cuatro), cuatro módulos sueltos iniciales, tres explosiones de cañón simultáneas y cuatro muertes simultáneas. Conserva los límites actuales de restos y efectos. El presupuesto se valida, no se promete que alcance 120.

Calentamiento: una oleada completa de 20s, guardada por separado para observar primeras apariciones. Pausa de 2s para escribir resultados fuera de la medición. Después 15 oleadas de 20s (al menos 300s) medidas. La semilla se fijará antes de cada ejecución; simulación normal, sin captureDeltaTime ni cambio de velocidad.

Cada oleada: 0s instanciar 16 T07 en cuadrícula x=(i%4-1.5)*3,z=2+floor(i/4)*3,y=.05; jugador (0,.05,-8). Entrada virtual del Input System: W/S/A/D y salto en primeros 1,3s, pulsos de disparo de pistola .5–2s. Cámara gira +/-18 grados mediante seno de 0,3rad/s. 2s desprender cuatro cañones; 3,1s colocar un módulo físico al alcance del jugador; 3,6–3,8s pulsar F real; 4,6–6,05s cargar/disparar por entrada nativa; 6,3s drenar energía para estado crítico; 6,8–7s pulsar G real; 7,2s detonar tres módulos críticos simultáneamente. 8/10/12s aplicar daño con Health a 73/48/23% en doce enemigos. 14s matar cuatro; 16s matar cuatro; 18s retirar únicamente los objetos de esa fixture. Restos usan sus TTL originales. Registrar cantidades realmente sucedidas, no solo programadas.

Salud invulnerable del jugador y daño invulnerable de enemigos fuera de las transiciones programadas son condiciones exclusivas de la fixture para repetir la misma carga. IA, NavMeshAgent, animación, movimiento, disparos, daño programado, robo y VFX permanecen activos. No se usa pooling de actores o armas para ocultar costes. Los resets de oleada pertenecen a la fixture, no cambian el loot del juego.

Desarrollo y Release se identifican por separado. Release usa BuildOptions.None, sin ScriptDebugging/AutoconnectProfiler; la fixture conserva telemetría ligera en memoria. GPU/CPU via FrameTimingManager con muestras ausentes/duplicadas excluidas. GC Alloc/Pause via contadores solo si disponibles. GC collections y memoria gestionada se registran también. Telemetría externa registra RSS y uso global de VRAM (no atribuirlo íntegramente al juego bajo WDDM).

Build: excluir únicamente compute shaders de com.unity.ai.inference en estas builds explícitas, porque el benchmark no contiene modelos ni workers de inferencia y la compilación previa quedó en ConvGeneric. No quitar paquetes ni tocar compute shaders de URP. API D3D11 y frame timing se aplican temporalmente durante build, con snapshots y restauración.

Corrección del entorno de pantalla: las ejecuciones exclusivas pueden perder 1080p al perder foco (Release de referencia inicial: 17.615 frames inválidos, descartada). Se prueba ventana de tamaño fijo con Display.Activate y Display.SetParams, API de Windows documentada por Unity 6000.5: https://docs.unity.com/en-us/engine/6000.5/script-reference/unityengine/display/setparams . Se valida Screen.width/height en cada frame. No se utiliza SetRenderingResolution, que la documentación limita a Android/iOS. Los resultados anteriores se conservan como diagnósticos, no como validación 1080p.
